# Аудит рендеринга Godot 4.8-dev (форк Ackustik1990/godot)

Ветка: `claude/great-thompson-u6dmhd`, база: `6210a2fd8` (upstream master).

Цель работы: найти узкие места рендера и доработать движок в сторону современных
техник (аналоги Nanite / Lumen), ускорить тени и отражения, добавить точку
подключения нейросетевых апскейлеров, а тяжёлые участки реализовать как можно
ближе к железу.

## 1. Методика

- Сборка: `scons platform=linuxbsd target=editor optimize=speed_trace tests=yes`,
  GCC 13.3, clang-format 22 для форматирования.
- GPU: программный Vulkan 1.4 (Mesa 25.2 lavapipe / llvmpipe, 4 потока CPU).
  Абсолютные миллисекунды поэтому на порядки больше, чем на видеокарте, но
  относительные ускорения и корректность картинки проверяются надёжно. На lavapipe
  любые лишние треугольники стоят дорого, что хорошо подсвечивает
  геометрические узкие места.
- Проверка корректности: автоматические сцены (скрипты в сессии), попиксельное
  сравнение кадров разных режимов, модульные тесты (`--test`), Vulkan
  synchronization validation (`VK_LAYER_KHRONOS_validation`, режим синхронизации).
- Профилирование CPU: `perf` на сцене из 30 000 объектов с направленной тенью,
  отдельные микробенчмарки для горячих функций.

Сквозной тест: 144 «камня» по 66 000 треугольников (≈25 млн примитивов в кадре
вместе с тенями), стена-окклюдер, направленный свет с тенями.

## 3. Архитектура (кратко)

`RenderingServer` → `RendererSceneCull` (видимость, LOD, свет, зонды) →
`RendererSceneRenderRD` → `RenderForwardClustered` (Forward+) / `RenderForwardMobile`
→ `RenderingDevice` (RD) → `RenderingDeviceGraph` (автоматические барьеры и
переупорядочивание команд) → драйверы Vulkan / D3D12 / Metal.
Компактный рендер (GLES3) использует отдельную реализацию в `drivers/gles3`.

## 4. Найденные проблемы и узкие места

Приоритет: **В** — высокий (заметно влияет на производительность или качество),
**С** — средний, **Н** — низкий.

### 4.1 Геометрия и LOD — В (исправлено)

- Автоматический LOD в Godot дискретный: на импорте генерируются несколько
  упрощённых индексных буферов, выбор делается на CPU для всего экземпляра.
  Это даёт «хлопки» при смене уровня и не масштабируется на плотную геометрию:
  большой объект целиком рисуется в детализации ближайшей к камере точки.
- Нет GPU-driven отрисовки: каждый экземпляр — отдельный draw call с полным
  индексным буфером, отсечение только на уровне экземпляра.

Сделано: виртуальная геометрия (раздел 5.1). Остаётся: поддержка `MultiMesh`,
скиннинга и blend shapes, стриминг кластеров (сейчас все кластеры резидентны в VRAM).

### 4.2 Окклюзионное отсечение — С (частично исправлено)

- Штатное окклюзионное отсечение (`servers/rendering/renderer_scene_occlusion_cull.h`,
  модуль `raycast`) растеризует запечённые `OccluderInstance3D` на CPU (Embree).
  Требует ручной подготовки окклюдеров, работает на уровне экземпляров и
  отстаёт на кадр.

Сделано: GPU-отсечение кластеров виртуальной геометрии по HZB без окклюдеров
(раздел 5.2). Остаётся: то же для обычных мешей (GPU-отсечение экземпляров) и
для теней.

### 4.3 Тени — В

- Каскады направленного света перерисовывают всех отбрасывающих тень каждый кадр.
  Патч для каскадов готовится отдельно, по договорённости будет изучен и доработан
  после получения коммита.
- `servers/rendering/renderer_scene_cull.cpp:2261` — `FIXME`: `z_max_cam`
  вычисляется, но не используется при построении ортографической камеры каскада.
  Глубина каскада может быть больше необходимой, что снижает точность глубины
  теней. Стоит учесть в патче каскадов.
- Отсечение отбрасывающих тень для каскадов (`RenderingLightCuller`) было
  скалярным.

Сделано: SIMD-тест в `RenderingLightCuller::cull_directional_light`; виртуальная
геометрия во всех проходах теней (LOD выбирается по основной камере, поэтому тени
совпадают с видимой геометрией).

### 4.4 Отражения — В (частично исправлено)

- Зонд с `UPDATE_ALWAYS` каждый кадр рендерит сцену 6 раз и заново фильтрует все
  уровни шероховатости (`RendererSceneCull::render_probes`). Ограничений нет:
  N видимых real-time зондов стоят 6N проходов сцены.
- Все зонды атласа рендерят грани через один общий кубический буфер
  (`ReflectionAtlas::color_buffer`), поэтому растянуть обновление одного зонда на
  несколько кадров по граням без отдельных буферов нельзя.
- Утечка: `LightStorage::_reflection_atlas_clear()` не освобождала этот кубический
  буфер и 6 его представлений граней (7 RID) при каждом пересоздании атласа.

Сделано: бюджет обновлений real-time зондов (раздел 5.4), исправление утечки.
Остаётся: трассировка отражений лучами (раздел 6).

### 4.5 Апскейлинг и TAA — С

- `render_forward_clustered.cpp` — `FIXME`: у FSR2 нельзя было сбросить накопление
  истории (смена камеры, телепорт), поэтому после резкой смены кадра были видны
  шлейфы; то же касалось TAA, MetalFX и пользовательских апскейлеров.
  **Исправлено** (раздел 5.6).
- `renderer_scene_render_rd.cpp:468` и `:912` — `FIXME`: проверка «можно ли
  применять эффекты» и вход постобработки используют целевое разрешение вместо
  внутреннего.
- `storage_rd/texture_storage.cpp:5500` — `FIXME`: storage-бит у текстур рендера
  запрашивается всегда, а не только когда нужен FSR. Это может мешать сжатию
  рендер-таргетов на части GPU.
- Не было способа подключить DLSS/XeSS/нейросетевой апскейлер без правки движка.

Сделано: API пользовательских апскейлеров (раздел 5.3).

### 4.6 CPU: подготовка кадра — С (частично исправлено)

Профиль сцены из 30 000 объектов: основное время CPU уходит в
`_fill_instance_data`, `_fill_render_list`, `_scene_cull` и
`RenderingLightCuller::cull_directional_light`. Все четыре ограничены промахами кэша:
элементы отсортированы по материалу, а данные экземпляров лежат в разных местах
памяти.

Сделано: SIMD-тест фрустума, radix sort для больших списков, программная
предвыборка (prefetch) данных в двух горячих циклах, кэширование сжатого AABB и
масштаба UV в кэше поверхности. Остаётся: SoA-раскладка данных экземпляров и
многопоточное заполнение списков рендера. Forward+ записывает каждый список
отрисовки в одном потоке; для очень больших сцен имеет смысл параллельная
запись через вторичные командные буферы.

### 4.7 Шейдинг — Н

- `shaders/scene_forward_lights_inc.glsl:256` — `FIXME`: при `roughness == 0`
  зеркальная составляющая от источников света отключается полностью (точечные
  блики на идеально гладких поверхностях пропадают).

### 4.8 RenderingDevice и драйверы — Н

- `drivers/vulkan/rendering_device_driver_vulkan.cpp:410`, `:3260`, `:5388` —
  `FIXME` о неполных масках стадий (geometry stage, детализация stage mask).
- Наблюдение при разработке HZB: запись в представления отдельных мип-уровней
  изображения и выборка из полного представления того же изображения в одном
  кадре на lavapipe давали выборку не из того диапазона уровней (`textureSize`
  возвращал размеры одного мипа). Synchronization validation ошибок не находит,
  код RD создаёт представления корректно. Поэтому HZB хранится в буфере, а для
  других эффектов с мип-цепочками стоит проверять это на разных драйверах.

## 5. Реализованные изменения

### 5.1 Виртуальная геометрия (аналог Nanite) — `b8d253c9c`

- Построение: `ArrayMesh.generate_virtual_geometry()` или опция импорта
  `meshes/generate_virtual_geometry`. Меш режется на кластеры по 128 треугольников
  (meshoptimizer), кластеры группируются, группы упрощаются с заблокированными
  границами. Ошибки монотонны, сферы вложены, поэтому любой срез иерархии не даёт
  трещин. Упрощение групп выполняется в пуле потоков. Формат данных
  версионирован (`servers/rendering/virtual_geometry_format.h`), проверяется при
  загрузке.
- Рендер (Forward+): кластеры всех мешей лежат в общих GPU-пулах. Для камеры и для
  всех проходов теней compute-шейдеры выбирают срез LOD по экранной ошибке,
  отсекают кластеры по фрустуму и конусу нормалей и уплотняют треугольники в
  индексный буфер. Каждый экземпляр рисуется одним indirect draw обычным
  пайплайном материала, поэтому поддерживаются все материалы и форматы вершин.
- Ограничения: только статичные непрозрачные материалы, не меняющие позиции вершин;
  без `MultiMesh`, скиннинга и blend shapes (для них остаётся обычный путь).

### 5.2 Окклюзионное отсечение кластеров — `22df01f27`

- Проход 1 (до depth pre-pass): кластеры, скрытые за HZB прошлого кадра
  (перепроецированным матрицей прошлой камеры), откладываются.
- Проход 2 (после depth pre-pass): строится HZB текущего кадра, отложенные кластеры
  проверяются заново, ставшие видимыми дорисовываются во втором depth pre-pass и
  в основных проходах. Видимая геометрия не теряется даже при движении камеры.
- HZB хранится в storage-буфере (уровни подряд); см. п. 4.8.
- Второй проход дописывает индексы в буфер первого, буфер рассчитан на пик обоих
  проходов, поэтому окклюзия не требует больше памяти, чем рендер без неё.
- Настройка `rendering/virtual_geometry/occlusion_culling` (по умолчанию включено).
  Работает для основной камеры с depth pre-pass, без MSAA и XR.
- Отладка: две найденные ошибки (переполнение отдельного буфера второго прохода и
  неверный диапазон мипов при выборке) закрыты; проверка — 0 отличающихся пикселей
  при движении камеры, отсутствие ошибок синхронизации.

### 5.3 Пользовательские апскейлеры — `b8d253c9c`

- Ресурс `RenderingUpscaler` (виртуальные методы доступны из GDExtension и
  скриптов) и режим `Viewport.SCALING_3D_MODE_CUSTOM` /
  `rendering/scaling_3d/custom_upscaler_class`.
- Апскейлер получает цвет, глубину, векторы движения, маску реактивности, джиттер,
  экспозицию, матрицы текущей и прошлой камеры и флаг сброса истории, и может
  работать либо через `RenderingDevice`, либо с нативным командным буфером
  (`DRIVER_RESOURCE_COMMAND_BUFFER`) для SDK вендоров (DLSS, XeSS, FSR 3+) и
  собственных нейросетей. Флаг сброса сейчас выставляется только при
  пересоздании буферов рендера (см. п. 4.5).
- Сами SDK вендоров в движок не включены (лицензии); интеграция делается
  расширением.

### 5.4 Бюджет real-time зондов отражений — `9e7f1de69`, утечка — `4fdd06cc9`

- `rendering/reflections/reflection_probes/max_update_always_per_frame`: сколько
  зондов `UPDATE_ALWAYS` обновлять за кадр. Первыми обновляются самые давно
  обновлённые, остальные сохраняют последнее отражение. 0 — прежнее поведение.
- В статичной сцене картинка с бюджетом совпадает с картинкой без бюджета.

### 5.5 CPU-оптимизации — `b8d253c9c`, `3b16bc549`

- `servers/rendering/frustum_cull_simd.h`: SoA-тест AABB против 6 плоскостей
  (SSE2/NEON) в `RendererSceneCull` и `RenderingLightCuller`.
- `servers/rendering/render_list_radix_sort.h`: стабильная LSD radix-сортировка по
  128-битному ключу с пропуском одинаковых разрядов, используется от 1024
  элементов (на меньших списках быстрее сортировка сравнением).
- Prefetch в `_fill_render_list` / `_fill_instance_data`, кэширование данных
  поверхности.

### 5.6 Сброс истории временных эффектов

- `Viewport.reset_temporal_history()` / `RenderingServer.viewport_reset_temporal_history()`:
  TAA, FSR2, MetalFX temporal и пользовательские апскейлеры отбрасывают накопленную
  историю на следующем кадре. Смена текущей камеры вьюпорта делает это
  автоматически. Закрывает `FIXME` о сбросе накопления FSR2.

## 6. Рекомендации и дальнейшие шаги

1. **Трассировка лучей (аналог Lumen).** В `RenderingDevice` уже есть API
   трассировки (BLAS/TLAS, ray tracing pipelines, `SUPPORTS_RAY_QUERY`), lavapipe
   поддерживает `VK_KHR_ray_query` и `VK_KHR_ray_tracing_pipeline`, так что это можно
   разрабатывать и проверять даже без видеокарты. Предлагаемый порядок:
   менеджер BLAS/TLAS → отражения лучами (гибрид: попадание на экране берёт цвет
   кадра, вне экрана — кэш освещения SDFGI или зонды) → RT AO/тени → диффузный GI.
2. **Каскады теней:** патч пользователя; учесть `FIXME` с `z_max_cam` и кэширование
   дальних каскадов.
3. **Виртуальная геометрия:** `MultiMesh`, стриминг кластеров, GPU-отсечение
   экземпляров обычных мешей, окклюзия в проходах теней.
4. **CPU:** SoA-данные экземпляров, многопоточная подготовка списков рендера.
5. Мелкие `FIXME` из раздела 4 (внутреннее разрешение для постобработки, storage-бит,
   блики при нулевой шероховатости).
